# `pr-triage` 设计与实现方案

- **适用基线**：`forge-kit v0.4.0`
- **落地形态**：纯 Skill + 分发清单登记 + `AGENTS.md` 轻量路由（不新增 `guard` 硬拦截器、不改 SQLite 账本 Schema、不增加外部依赖）

## 1. 背景与问题定义

PR 提交后，外部 AI Reviewer 常会产出大量“推演逻辑成立但工程 ROI 极低”的评论（尤其是前端交互层的自相矛盾或边角时序）。当前工作流在此节点存在**双极失效**：

1. **逻辑成立即修复（过度复杂化）**：Codex（Astra 系列）核验评论时，只要确认某路径在代码层面“理论上能触发”，就会直接动手修改，缺少对“真实发生频次 × 实质损失 vs. 系统复杂度代价”的过滤，导致 AI 之间来回加补丁、代码持续膨胀。
2. **人工否决后无脑顺从（丧失独立判断价值）**：当开发者出面解释“该路径真人极少遇到、无实质损失、不值得增加复杂度”时，Codex 会在同一上下文里立刻翻转立场直接放弃修改，不再坚持真正高危的问题，导致其意见失去第二双眼睛的价值。

同时需兼容两个现实约束：
- **SSOT / `INV-*` 非必选**：并非所有仓库或任务都走完 `full` 周期拥有 `ssot.md`，规则不能强依赖 `INV-*` 存在。
- **“人能做到 ≠ 人人都能做到”**：前端交互中几乎任何边角状态都能被人为操作出来，不能用二元的“是否可达”做判断，必须显式刻画**超低频 + 低成本自愈 + 复杂度税**的边界。

## 2. 设计目标与非目标

### 目标
- 将 **“验证评论成立”** 与 **“决定是否修复”** 拆分为强制两段式流程：Codex 先用 `gh` 拉取评论并完成只读初判（输出分诊表），用户二次确认后再动手改代码。
- 建立不依赖 `ssot.md` 的通用实质损失底线（有 `ssot.md` 时自动叠加 `INV-*` 作为增强信号）。
- 通过 **操作频次分档 × 自愈成本 × 复杂度税** 与 **正反校准锚点**，让模型稳定识别并默认过滤掉“超低频 + 无实质损失 + 增复杂”的噪声评论。
- 引入 **有限反顺从协议** 与 **按需盲审升级**（复用只读 `analyst`），避免用户一句“不用修”就让模型放弃真正高危的问题。
- 与 `v0.4.0` 的 `HANDED_OFF` / `ledger resume` / `ledger decide` / `ledger pr-sync` 交付流无缝衔接。

### 非目标
- 不新增 `PreToolUse` / `guard` 硬规则检查（该节点属于工程权衡，不适合静态熔断）。
- 不修改 `ledger` 数据库结构或新增 CLI 子命令。
- 不向 `core/AGENTS.md` 塞入大段细则（当前 `core/AGENTS.md` 为 7,405 bytes，需严格保持 `< 8,000` bytes）。

## 3. 核心判断框架

### 3.1 通用实质损失底线（不强依赖 SSOT）
- **若任务存在 `.workbench/specs/<task_id>/ssot.md`**：先对照 `INV-*` 与冻结外部契约，违背项直接视为触发红线。
- **无 SSOT 时（及所有任务的通用底线）**：满足以下任一条即视为**实质损失**：
  1. 资金、计费、积分、配额或核心业务权益错误；
  2. 权限越界、敏感信息泄露或安全边界失效；
  3. 持久化数据写脏、静默丢失或不可逆破坏；
  4. 核心主链路不可自愈阻断（例如按钮/页面永久锁死且无法恢复）；
  5. 导致用户已填写的大段表单或工作成果意外丢失。
- **低成本自愈（核心降噪阀）**：若未触碰上述红线，且用户通过**刷新页面、重开弹窗或重试一次**即可恢复正常，则判定为**无实质损失**。

### 3.2 三维评估矩阵

| 维度 | 分档定义 |
|---|---|
| **操作频次** | **L1 常规流**：正常用户按预期路径走就会遇到（常规提交、空态、常见弱网失败）<br>**L2 自然误操作**：常见人类习惯（连点提交、切 Tab 返回、输一半取消）<br>**L3 刻意折腾 / 复合时序**：需叠加多个偶发条件（请求返回几十毫秒窗口内切路由并改状态、多开 Tab 并行编辑同一对象、手动改 URL/存储进半残态） |
| **实质损失与自愈** | **触碰红线**：命中 3.1 实质损失底线或违背 `INV-*`<br>**低成本自愈**：未命中红线，刷新/重开/重试即可恢复 |
| **复杂度税** | **极低**：约 ≤ 5 行改动（补 `?.`、补 `disabled={loading}`、修拼写/类型），不引入新状态变量、锁或跨模块耦合<br>**显著增复杂**：需新增前端状态机、竞态锁、`AbortController` 链路、跨组件同步、复杂卸载清理或额外后端分支 |

### 3.3 处置结论与默认偏置

- **`Invalid`**：外部 reviewer 误读代码、基于过时 diff 或纯属幻觉 → 不修，给事实依据。
- **`Must-Fix`**：命中实质损失底线，或属于 L1 常规流缺陷 → 建议必须修。
- **`Cheap-Fix`**：虽非高危，但改动极小且不引入额外状态/耦合（顺手修比来回解释更省事）→ 建议顺手修。
- **`Won't-Fix`（默认偏置）**：**L3（或 L2 且低成本自愈 + 无实质损失）+ 修复会显著增加复杂度** → **默认判 `Won't-Fix`**，严禁因“逻辑上能推演出来”就升级为 `Must-Fix`。

### 3.4 正反校准锚点（内置于 Skill）
为防止模型对抽象措辞漂移，Skill 内必须保留 4～5 条具体校准示例：
- **Won't-Fix 锚点**：
  - 弹窗关闭动画期间强行二次点击触发重复只读请求，修它需加状态锁与定时器清理 → `Won't-Fix`。
  - 多开两个浏览器 Tab 并行修改同一非协同配置项导致后写覆盖先写，修复需整套乐观锁与冲突 UI → `Won't-Fix`。
  - 切换路由瞬间短暂闪过旧列表，下次进入或刷新即同步且无脏写 → `Won't-Fix`。
- **Cheap-Fix 锚点**：
  - 漏写 `?.` 判空或按钮漏绑 `disabled={loading}`，几行内解决且无新状态耦合 → `Cheap-Fix`。
- **Must-Fix 锚点**：
  - 表单本地校验失败后 loading 未重置，导致按钮永久锁死且刷新后用户输入全丢 → `Must-Fix`。
  - 前端未防连点且后端无幂等校验，连点两次导致重复扣费或创建脏订单 → `Must-Fix`。

## 4. 两段式工作流（适配 `gh` 与 v0.4 交付体系）

### Pass 1：只读拉取与分诊（严禁先改代码）
1. **拉取评论**：用 `gh` 拉取目标 PR 当前未解决的 review comments 与 review body（区分人工 reviewer 与 AI reviewer，但统一按事实核验）。
2. **只读核验**：逐条对照当前分支代码与 diff（若有 `ssot.md` 一并对照），剔除 `Invalid` 项。
3. **输出紧凑分诊表并暂停**：按以下列输出汇总表，明确标出 Codex 的建议，**严禁在用户确认前修改任何业务代码**：

| # | 文件/位置 | 问题摘要 | 频次 | 实质损失/自愈 | 复杂度 | 建议 | 一句话理由 |
|---|---|---|---|---|---|---|---|

### Pass 2：用户二次裁决、有限反顺从与执行闭环
1. **用户拍板**：用户确认哪些条目修、哪些不修，或对 Codex 的判断提出质疑。
2. **有限反顺从协议（Anti-Sycophancy）**：
   - 当用户否决某条 `Must-Fix`（表示“这个不用修”）时，**禁止立刻顺从改口**。
   - Codex 必须对照代码做**最多一轮证据反证**：
     - 若能指出用户尚未注意到的具体代码证据，证明会触碰 3.1 实质损失底线、不可自愈或存在极低复杂度修法，**必须明确反驳并亮出证据**，交由用户做最终裁决；
     - 若核验后拿不出新证据，才允许撤回，且必须显式说明自己此前高估了哪一维（频次还是损失），避免空泛认错。
   - **按需盲审升级**：仅当高风险争议双方拉锯不下时，派生隔离上下文（`fork_turns="none"`）的只读 `.codex/agents/analyst.toml`，仅传入 diff、该条评论和可选 `ssot.md`（**刻意不传入“用户倾向于不修”的上下文暗示**），获取独立风险与复杂度评估。日常低风险评论不触发，控制延迟与成本。
3. **执行与 v0.4 账本/PR 闭环**：
   - **有确认修改项**：
     - 若关联任务在账本中处于 `HANDED_OFF` 状态，先按 `ship` 模式 B 执行 `.workbench/bin/ledger resume <task_id>`；
     - 仅修改用户确认的条目，不顺带扩大修复范围；
     - 完成后按任务原风险深度重跑适用验证与评审（`wb-verify` / `forge-review` 或定向检查），推送新提交并运行 `ledger pr-sync <task_id> --repo <repo> --branch <branch>`（若走模式 B 则重新 `ledger handoff` 并更新 PR 见证）。
   - **`Won't-Fix` / `Invalid` 项留痕与回复**：
     - 若任务已建账，将 `Won't-Fix` 裁决写入 `ledger decide`（记录不修前提、可接受边界与复杂度权衡），防止后续轮次或上下文压缩后反复重修；
     - 为每条 `Won't-Fix` / `Invalid` 起草简洁克制的 PR 回复（写明：已知该边界、当前前提下为何不修、若未来前提变化何时重议），由用户确认后发送或直接贴回 PR 终结拉锯。

## 5. 具体实现清单

### 5.1 新增 Skill：`core/.agents/skills/pr-triage/SKILL.md`
- **Frontmatter**：
  - `name: pr-triage`
  - `description`: 覆盖拉取并分诊 PR 外部评审意见（尤其是 AI reviewer 评论），按频次、实质损失/自愈成本与复杂度做两段式裁决、有限反顺从及 `Won't-Fix` 留痕回复；触发词包含 `pr-triage`、`看下 PR 评论`、`处理 PR review`、`拉一下评论`、`PR 评审意见`。
- **正文结构**（保持精炼，与现有 Skill 风格一致）：
  1. 核心纪律（禁止见评论直接改代码；先分诊表后二次确认；`INV-*` 可选、通用红线常驻）；
  2. 判断框架（3.1 通用红线 + 3.2 三维表 + 3.3 默认偏置 + 3.4 校准锚点）；
  3. Pass 1 步骤（`gh` 拉评论 → 只读核验 → 输出分诊表暂停）；
  4. Pass 2 步骤（有限反顺从 → 按需 `analyst` 盲审 → 衔接 `ledger resume` / 修改验证 / `ledger pr-sync` → `ledger decide` 与 PR 回复草稿）。

### 5.2 注册分发：`kit.toml`
在 `[managed].copied_dirs` 中新增一项：
```toml
".agents/skills/pr-triage",
```
使 `forge init` 与 `forge sync` 自动将该 Skill 同步至目标工作台。

### 5.3 轻量路由：`core/AGENTS.md`
在「调度与流程入口」末段按阶段列表中追加 `pr-triage（PR 评审分诊）`（约 30～50 bytes），确保 `wc -c < core/AGENTS.md` 仍远低于 `8,000` bytes 上限（当前 7,405 bytes，改动后约 7,450 bytes）。

1. 检查现有 `tests/` 中对 `kit.toml` / `forge init` / `forge sync` / `forge doctor` 的技能列表断言，补充 `pr-triage` 覆盖（若测试校验了具体目录清单）。
