# 实施需求

**输入**为需求、目标仓及分支、授权终点和实例工作说明。先用 `forge ledger status` 恢复既有任务，或用 `forge ledger open` 登记 repo、branch、endpoint 和 depth。一项正式任务沿用同一账本。

1. **定档和确认。** 默认完整模式。只有改动局部单纯、未触及核心不变量或关键契约、主干已有覆盖三者均满足才用轻量模式。用 grill 收敛需求。
2. **冻结。** 完整模式先确认 SSOT。将同一 SSOT 分别交给两个无共享历史的 implementer，各自产出技术规格和测试规格，互不读取对方产物。独立 reviewer 按正确性、性能、兼容性和简单性评技术规格，另按完备性、正确性评测试规格。修正阻断项，用户确认后三份文件一起冻结。轻量模式以用户确认的 `scope.md` 冻结。使用 `forge ledger freeze <task-id>`。
3. **双轨实施。** 规格冻结后同时派发两个独立上下文，约定各自的文件归属。完整模式给实现作者 SSOT 与技术规格，给测试作者同一 SSOT 与测试规格。轻量模式给两位作者同一份 scope。两位作者各自依据冻结输入开工，均可在另一方尚未产出文件时推进。测试覆盖公开入口、异常路径和存量行为，夹具需能清理。契约用例落盘后用 freeze 的 `--lock-tests` 绑定相应路径。若确认需要改动冻结承诺，经用户裁决后 amend 并重验受影响下游。
4. **独立审查及验证。** 使用 review。每次调用评审 CLI 前先看 `forge ledger reviews <task-id>`，由工作 agent 选择本轮角色。修复阻断项后用 verify 在待交付版本执行静态、动态及集成验证。
5. **交付。** 使用 ship 到达实例及用户指定的终点。默认取得 PR 合入 main 的远端回执。外部 PR 意见按 pr-triage 裁决并验证新版本。

**输出与完成条件**为冻结规格、绑定实际 SHA 的评审和验证证据、交付回执及账本状态。正式移交时报告接收方和见证，外部条件未满足时说明实际停在哪一步。
