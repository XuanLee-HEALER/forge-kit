# grill：需求追问与 SSOT 定稿

在进入编码或技术方案前，把模糊需求压缩成无歧义、可独立验证的 **Single Source of Truth**（默认落盘于工作台私有目录 `.workbench/specs/<task_id>/ssot.md`，不自动写入业务仓；仅用户明确要求时再移入业务仓）。

## 原则

1. **先查代码与事实，再问用户**：入口、现有表结构、现有接口与调用方自行查证；只把真正改变用户权益、业务口径、兼容边界或可接受损失的分歧列出来追问。
2. **只定“是什么与外部契约”，不写“内部怎么实现”**：`ssot.md` 必须能同时作为**技术方案 Agent** 与**独立 Hurl 测试 Agent** 的共同上游——因此必须锁死**外部接口契约**（URL/RPC、入参/出参字段名、错误码、状态机跃迁、权限/计费不变量），避免两个独立 Agent 各猜一套字段名；同时**禁止**把内部实现选型、表索引细节或缓存结构写进 `ssot.md`。
3. **不变量编号可追溯**：每条业务底线用 `INV-1`, `INV-2`… 唯一编号，供后续 `test-spec.md` 与 Hurl 用例逐条映射覆盖。

## 步骤

1. **建档与现状核查**：确定或创建 `task_id`（`.workbench/bin/ledger open ... --depth full`），读取受影响仓库相关代码/文档，核清既有约束。
2. **结构化追问**：按优先级分批列出未决口径（每项附现状 + 推荐方案 + 具体代价），逐项与用户对齐直至无歧义：
   - 业务不变量（特别是资金/积分/额度/权限服务端权威边界、幂等与并发语义）；
   - 核心与异常衍生流程（失败回滚、边界空值、历史存量数据兼容）；
   - 外部接口契约（精确路径、HTTP method、字段名/类型/必填性、错误码与响应结构）；
   - 交付终点（默认 `local`，或 `fat`/`pr`/`prod`）与非目标范围（Explicit Non-Goals）。
3. **产出 `ssot.md` 并请用户拍板**：
   写入 `.workbench/specs/<task_id>/ssot.md`，必须包含 5 节：
   - `## 1. 目标与非目标`
   - `## 2. 业务不变量（INV-*）`
   - `## 3. 核心与异常业务流程`
   - `## 4. 冻结的外部接口契约`（路径/字段/枚举/错误码/状态机，不含内部实现）
   - `## 5. 存量兼容与验收边界`
4. **交接下游**：用户明确确认 `ssot.md` 后，转入 `feature` 的 **Stage 1（双独立隔离上下文并行生成 `tech-spec.md` 与 `test-spec.md`）**。
