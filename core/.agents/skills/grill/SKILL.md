# 需求定稿

**输入**为原始需求、已有承诺、目标仓及可查证的外部行为。规格写到实例的 `.workbench/specs/<task-id>/`。

按目标仓和拟改路径运行 `forge apply check --repo <repo> --path <path> --json`：UNCHANGED 直接读卡，CHANGED 或 BROKEN 交给 apply 复核，UNMAPPED 的长期关注域或复杂陌生域用 focus 快绘，一次性小修可跳过建卡。工程约定记录一次；仅在核心实体、入口、边界变化或发现未记录禁区时回写实例卡并更新已核验 SHA。

1. 区分背景、举例和正式承诺，明确哪些结果已经操作者确认。检查真实入口、历史数据及调用方，确认受影响的人、触发条件与可观察结果。对多种合理解释，说明适用场景、发生频率、用户损失、恢复成本和实现代价。能由既有证据回答的问题自行解决。
2. 从工作台根读取 `.agents/skills/review/references/risk-rubric.md`，界定必守承诺与可容忍风险。把会改变业务承诺、权限、验收边界或可接受损失的取舍提交操作者裁决。新增限制或验收用例前，记录可达的真实入口、具体损失和现有机制的覆盖缺口。
3. 涉及核心实体、状态机或公共契约时，检查新增字段或状态是否与实体职责正交、是否需要放宽现有不变量、同类需求出现次数及无关调用方的受影响范围。第二至第三次出现同类需求时评估模型演进。发现模型污染信号时，请操作者选择 A 演进模型与不变量、B 隔离特例、C 调整需求或退回。选 B 时，将适用范围、下线条件和重议触发写入规格，并用 `forge ledger decide` 记录同一决定。再次叠加同类特例或达到下线条件时，请操作者重议。
4. 完整模式写 `ssot.md`，列目标、编号不变量、正常及异常流程、外部契约、存量兼容和验收边界。字段、状态、失败行为与交付结果须可独立验证。轻量模式按 feature 的三个准入条件写 `scope.md`，列修改范围、主干覆盖依据及补充测试用例。两种规格均写明必守承诺、允许的风险及其前提，并记录已确认的决定和重议条件。

**输出与完成条件**为用户明确确认的规格及决定。完整模式取得操作者确认 SSOT 和开工授权后，将同一份 SSOT 交给独立的方案作者和用例作者；轻量模式由 feature 核对确认并冻结。
