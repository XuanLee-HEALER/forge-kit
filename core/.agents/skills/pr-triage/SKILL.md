# PR 评审分诊

功能线程对实现负责，交出 PR 前应能说明每条待处理意见的结论，并验证最终 HEAD。发布线程只接收就绪 PR，按 ship 模式 B 核验、合并和发版。若移交后发现实现问题或 HEAD 漂移，发布线程暂停受影响批次，交回功能线程处理。

## 第一轮 · 只读核验，给出建议后暂停

1. 确认仓库、PR、目标分支和当前远端 HEAD。用 `gh pr view` 读取 review 正文，用 `gh api graphql` 读取 `reviewThreads` 的 `isResolved`、位置和评论上下文。检查分页（含长线程及 reviews），收齐未解决线程及正文中的独立意见，合并重复项、标明人工或 AI 来源。数据缺失时说明覆盖范围。
2. 用 `gh pr diff` 和该 HEAD 的代码逐条核验；本地检出不同版本时以 PR 版本为准。过时的行号仍须检查当前实现。若有任务规格，读取 `.workbench/specs/<task_id>/ssot.md` 及冻结契约。没有 SSOT 也照常分诊。
3. 输出表格，每项保留可引用的编号和代码事实。此轮只读，停在表后等用户确认修哪些项。即使全部是顺手修，也等裁决。

| # | 文件/位置及来源 | 问题摘要 | 操作频次 | 实质损失/自愈 | 修复复杂度 | 建议 | 一句话依据 |
|---|---|---|---|---|---|---|---|

**逐条判断**

- 评论与当前实现矛盾或问题已修复，列为 **Invalid**，指出代码依据。证据不足时写明缺什么，保留待核实状态。
- **L1** 是预期操作或常见失败路径，**L2** 是连点、切 Tab 返回等自然误操作，**L3** 需要刻意构造或多个偶发时序重合。按产品的真实用法判断频次。
- 违反适用的 `INV-*` 或冻结契约，以及资金、计费、配额或权益错误，权限越界或泄密，持久化脏写或静默丢失，核心流程不可自愈，或大量输入、工作成果丢失，均为 **Must-Fix**。L1 的真实流程缺陷同样判 Must-Fix，修法便宜只影响复杂度栏。只有能保住用户成果，刷新、重开或重试一次的恢复成本才算低。
- 其余成立项权衡收益和复杂度。几行局部改动即可解决且无需新状态或耦合，选 **Cheap-Fix**。L3 或低成本自愈的 L2，损失轻微且需要新增状态、锁或跨组件同步，默认 **Won't-Fix**。

| 校准情境 | 建议 |
|---|---|
| 关闭动画里再次点击，仅多一次只读请求；修复要加锁和定时清理 | Won't-Fix |
| 路由切换时短暂闪过旧列表，进入后自动同步，无脏写 | Won't-Fix |
| 罕见的旧数据漏填可选备注，局部补一个可选链即可恢复展示 | Cheap-Fix |
| 校验失败后按钮锁死，刷新会丢失已填长表单 | Must-Fix |
| 重复提交会重复扣费，服务端也没有幂等保障 | Must-Fix |

## 第二轮 · 按裁决执行

- 用户否决 Must-Fix 时，最多再核验一轮。如果有新证据，指出触发路径、具体损失或低成本修法，让用户最终裁决；若没有，明确先前高估了频次、损失或低估了成本。仅在高风险争议仍未解决时，才请只读 `analyst` 盲审，使用独立上下文（`fork_turns="none"`），只给相关 diff、评论和可用的 SSOT，省去双方立场。
- 只实施确认项。已移交的任务确需改实现，由功能线程先 `ledger resume <task_id>`。按原风险深度运行适用的验证和独立评审，推送并核对新 HEAD；有账本时按分支执行 `ledger pr-sync <task_id> --repo <repo> --branch <branch>`。模式 B 就绪后按 ship 重新 handoff 并更新 PR 的三条见证。
- 在 OPEN 任务上用 `ledger decide <task_id> --key <稳定条目标识> --summary "<前提、可接受边界和复杂度权衡>"` 记录已裁决的 Won't-Fix。只有跳过项时保持已有移交状态。为 Won't-Fix 和 Invalid 起草简短回复，写明适用前提、事实依据及何时重议；用户确认发送后再贴回 PR。
