# PR 评审分诊

**输入**为目标仓、PR、远端 HEAD、未解决评论及可用规格。功能线程对实现负责，交出 PR 前应能说明每条待处理意见的结论，并验证最终 HEAD。发布线程只接收就绪 PR，按 ship 的移交流程核验、合并和发版。若移交后发现实现问题或 HEAD 漂移，发布线程暂停受影响批次，交回功能线程处理。

## 第一轮 · 只读核验，给出建议后暂停

1. 确认仓库、PR、目标分支和当前远端 HEAD。用 `gh pr view` 读取 review 正文，用 `gh api graphql` 读取 `reviewThreads` 的 `isResolved`、位置和评论上下文。检查分页（含长线程及 reviews），收齐未解决线程及正文中的独立意见，合并重复项、标明人工或 AI 来源。数据缺失时说明覆盖范围。
2. 用 `gh pr diff` 和该 HEAD 的代码逐条核验。本地检出不同版本时以 PR 版本为准。过时的行号仍须检查当前实现。若有任务规格，读取已冻结的 ssot.md 或 scope.md。没有 SSOT 也照常分诊。
3. 输出表格，每项保留可引用的编号和代码事实。此轮只读，停在表后等用户确认修哪些项。即使全部是顺手修，也等裁决。

| # | 文件/位置及来源 | 问题摘要 | 操作频次 | 实质损失/自愈 | 修复复杂度 | 建议 | 一句话依据 |
|---|---|---|---|---|---|---|---|

**逐条判断**

- 评论与当前实现矛盾或问题已修复，列为 **Invalid**，指出代码依据。证据不足时写明缺什么，保留待核实状态。
- 从工作台根读取 `.agents/skills/review/references/risk-rubric.md`，对照判据给出 Must-Fix、Cheap-Fix 或可接受风险的证据。可接受风险在建议栏写 **Won't-Fix**，等待操作者裁决。

## 第二轮 · 按裁决执行

- 用户否决 Must-Fix 时，最多再核验一轮。如果有新证据，指出触发路径、具体损失或低成本修法，让用户最终裁决；若没有，明确先前高估了频次、损失或低估了成本。仅在高风险争议仍未解决时，才请只读 `analyst` 盲审，使用独立上下文（`fork_turns="none"`），只给相关 diff、评论和可用的 SSOT，省去双方立场。
- 只实施确认项。已移交的任务确需改实现，由功能线程先 `forge ledger resume <task_id>`。按原风险深度运行适用的验证和独立评审，推送并核对新 HEAD；有账本时按分支执行 `forge ledger pr-sync <task_id> --repo <repo> --branch <branch>`。可移交时按 ship 重新 handoff 并更新 PR 的三条见证。
- 在 OPEN 任务上用 `forge ledger decide <task_id> --key <稳定条目标识> --summary "<前提、可接受边界和复杂度权衡>"` 记录已裁决的 Won't-Fix。只有跳过项时保持已有移交状态。为 Won't-Fix 和 Invalid 起草简短回复，写明适用前提、事实依据及何时重议；用户确认发送后再贴回 PR。

**输出与完成条件**为逐项分诊结论、已确认修复及验证版本、待裁决项或回复草稿。核对当前 PR HEAD 及其见证，送达外部回复须有授权。
